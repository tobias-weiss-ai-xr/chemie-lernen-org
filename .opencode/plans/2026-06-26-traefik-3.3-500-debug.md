# chemie-lernen.org live state — 2026-06-26

## RESOLVED 2026-06-27

Root cause was **not** Traefik config — it was a **corrupted Docker network sandbox**.
Both hugo-chemie-lernen-org and chemie-chat-api were registered on `traefik-public`
but had no IP address (empty `EndpointID` + `IPAddress` in container inspect).

**Fix**: `docker compose rm -fs <service>` + `docker network connect traefik-public <container>` + `docker compose start <service>` for each container.
Secondary fix: set `NETWORKS=1` on socket-proxy (was `0`, blocking Docker network API).

No Traefik config changes were needed. The file provider `loadbalancer.server.url`
overrides were also unnecessary and were left in place as active config.

## What works ✅

- Let's Encrypt cert for `chemie-lernen.org` (issuer: YR2, valid until Sep 24 2026) is issued and in `traefik/tls_letsencrypt.json`
- Traefik 3.3 is running and healthy on ports 80/443
- HTTP (port 80) correctly redirects 301 → HTTPS
- TLS handshake succeeds (CN=chemie-lernen.org, Let's Encrypt YR2, cert verify OK)
- `chemie-lernen.org` resolves to 178.254.2.90 (public IP)
- Direct backend access works:
  - `curl http://172.22.0.10:80/` → 200 (hugo)
  - `curl http://172.22.0.9:3001/api/health` → 200 (chat-api)
- Docker provider is configured with `network: "traefik-public"` (correct)
- Chemie-lernen.org services have the correct labels (incl. `traefik.docker.network=traefik-public`)

## What doesn't work ❌

**All HTTPS routes return 500 with `OriginStatus: 0`.** Traefik never connects to the backend.

Key evidence from Traefik access log:

```json
{
  "RouterName": "chemie@docker",
  "RequestPath": "/",
  "DownstreamStatus": 500,
  "OriginStatus": 0,    ← Traefik never connected to origin
  "OriginDuration": 0,  ← no time spent on origin
  "Overhead": 1656357
}
```

Traefik error log (the actual blocker):

```
{"level":"error","providerName":"docker",
 "container":"hugo-chemie-lernen-org-...",
 "error":"service \"chemie\" error: unable to find the IP address
         for the container \"/hugo-chemie-lernen-org\":
         the server is ignored"}
```

The same error happens for `chemie-chat-api` (also "unable to find IP").

## Root cause (best guess)

Traefik 3.3 + socket-proxy (lscr.io/linuxserver/socket-proxy) + docker
provider has a compatibility issue. The docker provider queries the
docker API via `tcp://socket-proxy:2375`, gets the container
metadata, but the network resolution step returns "no IP" even
though the container is on `traefik-public` with a known IP
(172.22.0.10 for hugo, 172.22.0.9 for chat-api).

A file provider override (with explicit `loadBalancer.servers[0].url
= http://172.22.0.10:80`) shows the same `OriginStatus: 0`
behavior — the file provider's service can't be reached either.

## Next steps to investigate

1. **Try the old Traefik v2.9 image** — the new v3.3 has known docker
   provider issues with some socket-proxy setups. Reverting to v2.9
   (with `mytlschallenge` and `letsencrypt` resolvers) might fix it.
2. **Check socket-proxy logs** — the socket-proxy might be filtering
   out the `/containers/json` response or the IP lookup.
3. **Try mounting the docker socket directly** instead of via
   socket-proxy (`-v /var/run/docker.sock:/var/run/docker.sock:ro`).
4. **Check iptables / nftables** on the host — the `policy DROP` on
   `INPUT` chain might be blocking outgoing connections from
   Traefik to non-gateway IPs (despite wget from inside Traefik
   working). The docker provider might be using a different
   connection path that hits the firewall.
5. **Enable Traefik debug log** to see the actual loadBalancer
   connection attempt: set `LOG_LEVEL=DEBUG` in the Traefik
   container env.
